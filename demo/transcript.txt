$ ruby2shell playbook
ruby2shell playbook - first hour after the 18/11/2026 Ruby2Shell disclosure

1. Upgrade Ruby first - this is a runtime flaw, not a gem
  Upgrade to the fixed build for your line: 3.3.14, 3.4.13 or 4.0.10 (released 18/11/2026). Updating gems or Rails does not help: the bug is in the interpreter. Rebuild every image from the fixed tags (ruby:4.0.10, ruby:3.4.13, ruby:3.3.14 - official Docker images rebuilt 19/11/2026) and restart every process so the fixed Ruby is the one running.

2. Ruby 3.2 and earlier: there is no patch - upgrade
  Ruby 3.2 and earlier are end of life and will not receive these fixes, but they carry the same code back to 2.4.0. The only move is upgrading to a supported Ruby (3.3.14, 3.4.13 or 4.0.10). Do not wait for a patch that is not coming.

3. Self-hosted products: install the vendor fixed release
  GitLab 19.6.1 / 19.5.8 / 19.4.10, Mastodon 4.7.6 (also 4.6.12, 4.5.22, 4.4.29), OpenProject 17.9.8 (also 17.8.3), Discourse base image 2.0.20261119-0203. Chatwoot fixed in 4.20.1. GitHub Enterprise Server (3.22.5 and earlier) still had no fixed release yet on 20/11/2026 - watch the vendor and treat those installs as exposed. Check with: ruby2shell check --product gitlab --product-version 19.6.0

4. Patch internet-facing Rails and classic Sinatra first
  Default Rails and classic-style Sinatra are reachable without authentication (Rack::MethodOverride calls .upcase on the _method parameter). Plain Rack and other frameworks are not exposed by default. Patch the internet-facing apps first, then workers and build images.

5. The patch window is days: the PoC lands 25/11/2026
  Veria Labs will publish a proof of concept demonstrating RCE on stock Rails on 25 November 2026, or later if major vendors have not shipped a fix by then. Ruby is already aware of non-public PoCs that reach RCE in some scenarios. No exploitation in the wild was reported as of 20/11/2026, and the CVE is not in the CISA KEV catalog as of the 2026-11-18 catalog version.

6. Verify the fix
  Re-run: ruby2shell scan --app <dir> (or ruby2shell check <ruby-dir> --app <dir>) and confirm SAFE on the fixed build. Confirm the running process uses the fixed Ruby (ruby -v in the deployed image), not just the lockfile. Then re-run the other six flaws as a checklist: the same release fixes 7 flaws (see explain siblings).

7. What NOT to do
  Do not send a crashing sharp-s payload at a live app to 'test' it - that is the exploit path, and this tool never does it. Do not run exploit code from untrusted repositories (PoC repos for this CVE already exist). Do not trust a clean bundle audit: bundler-audit checks gems, not the interpreter, so it cannot see this flaw.
